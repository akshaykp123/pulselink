Q1: What are SQL Aggregations (GROUP BY, COUNT), and why run them in PostgreSQL instead of JavaScript memory?
Interviewer's Goal: Tests understanding of database query execution vs application memory bottlenecks.

If an application pulls 1,000,000 raw click records into Node.js to group and count them in memory (e.g. Array.reduce), it consumes hundreds of megabytes of RAM and freezes the Node.js single-threaded event loop.

PostgreSQL is compiled in C and optimized to process aggregations directly on disk using our B-Tree indexes. It executes GROUP BY and COUNT across a million rows in under 10ms and transmits only a few bytes of summary numbers back to Node.js.

Q2: What is the difference between COUNT(*) and COUNT(DISTINCT ip_hash)?
Interviewer's Goal: Tests aggregate SQL functions and telemetry calculation.

COUNT(*) calculates the absolute total number of rows (Total Clicks) matching the url_id, regardless of who clicked it.

COUNT(DISTINCT ip_hash) inspects the anonymized visitor hashes and counts only unique occurrences (Unique Visitors). If a single person clicks the link 20 times from the same device, COUNT(*) returns 20, while COUNT(DISTINCT ip_hash) returns 1.

Q3: How does date_trunc('hour', clicked_at) work, and why is it useful for time-series charts?
Interviewer's Goal: Tests date/time manipulation in SQL for data visualization.

date_trunc('hour', timestamp) truncates a full timestamp to the beginning of its specified interval by zeroing out minutes, seconds, and milliseconds (e.g. 14:23:45.120 becomes 14:00:00.000).

This creates uniform hourly 'time buckets'. When combined with GROUP BY time_bucket, all clicks that occurred within that hour are aggregated into a single data point, enabling charting libraries (like Recharts) to plot smooth time-series curves.

Q4: Why did we use Promise.all to execute our 5 analytics queries? How does that interact with our Connection Pool?
Interviewer's Goal: Tests asynchronous JavaScript concurrency and database pool utilization.

If we executed the 5 queries sequentially using await one after another, the total latency would be the sum of all 5 queries (e.g. 10ms × 5 = 50ms).

By wrapping them in Promise.all([ ... ]), Node.js fires all 5 queries simultaneously. Our pg.Pool immediately loans out 5 available client connections in parallel, allowing PostgreSQL to execute all 5 queries concurrently across CPU cores. The total response time equals the single slowest query (~10ms total).

Q5: What is an Express Middleware, and what is the role of next()?
Interviewer's Goal: Tests Express request lifecycle architecture.

A Middleware is a function with access to the request (req), response (res), and the next function in the application's request-response cycle.

It acts as an interceptor. If the middleware validates that the request is permitted (under the rate limit), it calls next() to pass control to the subsequent middleware or route handler. If the request violates policy, it terminates the cycle early by returning a response (e.g. res.status(429)), preventing downstream code from executing.

Q6: Explain the "Fixed Window Counter" algorithm using Redis INCR and EXPIRE.
Interviewer's Goal: Tests algorithmic knowledge of rate limiting.

In a Fixed Window Counter algorithm:

  1. We construct a unique Redis key per client IP: ratelimit:<route>:<ip>.
  2. We call redis.incr(key). If the key does not exist, Redis initializes it with value 1.
  3. If the count is 1 (first request of the window), we set an expiration timer: redis.expire(key, 60).
  4. On subsequent requests, INCR increments the counter. If the counter exceeds the maximum allowed threshold before the 60-second TTL expires, requests are rejected with HTTP 429.
  5. Once the TTL expires, Redis automatically deletes the key, resetting the counter for the next window.

Q7: Why is Redis INCR considered "atomic", and why does that matter for rate limiting?
Interviewer's Goal: Tests concurrency, multi-threading, and race condition prevention.

An atomic operation executes completely in a single step without the possibility of interruption or interleaving.

If rate limiting was done in a traditional database with read-then-write (SELECT count ... UPDATE count = count + 1), concurrent requests arriving at the exact same millisecond could read the same count simultaneously, causing a Race Condition where an attacker bypasses the limit.

Because Redis is single-threaded, INCR executes atomically in RAM. Every increment is guaranteed to see the exact incremented value of the previous operation, making race conditions impossible.

Q8: What is the limitation of Fixed Window Counter vs Sliding Window?
Interviewer's Goal: Tests advanced rate limiting algorithms (Senior/Mid-level question).

The main limitation of a Fixed Window algorithm is the Boundary Burst Problem.

If a user sends 5 requests at second 59, and 5 more requests at second 01 of the next window, they have sent 10 requests within a 2-second window without triggering the 5-requests/minute limit.

To eliminate this edge case, advanced production systems use a Sliding Window Log (storing timestamps in a Redis Sorted Set ZSET) or a Token Bucket algorithm.

Q9: What are the standard HTTP headers returned by a rate limiter?
Interviewer's Goal: Tests API standards, RFC compliance, and developer experience.

Industry-standard rate limiting headers include:

  • X-RateLimit-Limit: The maximum number of allowed requests in the current window.
  • X-RateLimit-Remaining: The number of requests remaining in the current window.
  • X-RateLimit-Reset: The number of seconds until the rate limit window resets.
  • Retry-After: (Returned on HTTP 429) Specifies the exact number of seconds the client must wait before retrying.

Q10: What is the "Fail-Open" vs "Fail-Closed" strategy in rate limiting?
Interviewer's Goal: Tests system reliability trade-offs and disaster recovery design.

When a rate limiter's backing store (Redis) experiences a network crash or outage:

  • Fail-Closed: The system blocks ALL incoming traffic until Redis recovers. This maximizes security but causes a complete outage for legitimate users.
  • Fail-Open: The middleware catches the Redis error, logs an alert, and calls next() to allow requests through to the database.
In our application, we implemented Fail-Open: a temporary cache outage will degrade DDoS protection slightly, but guarantees 100% availability for legitimate users.
