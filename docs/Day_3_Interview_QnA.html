Q1: What is Redis, and why is it so much faster than relational databases like PostgreSQL?
Interviewer's Goal: Tests understanding of In-Memory architectures vs. Disk-based storage.

Redis (Remote Dictionary Server) is an open-source, in-memory key-value data structure store.

PostgreSQL writes and reads data from persistent Disk (SSD/HDD), which involves disk I/O, file system page caching, and buffer pool traversals (typically 10–40ms). In contrast, Redis keeps all data exclusively in RAM (Random Access Memory). RAM access operations execute in nanoseconds, allowing Redis to read and write key-value pairs in sub-millisecond speeds under high concurrency.

Q2: Explain the Cache-Aside Pattern (Lazy Loading). What are its benefits?
Interviewer's Goal: Core system design caching pattern assessment.

In the Cache-Aside Pattern, the application code directly orchestrates communication between the cache and the primary database:

  1. Application receives a request and checks the cache first (redis.get).
  2. Cache Hit: Cache returns data immediately; application returns response (PostgreSQL is never touched).
  3. Cache Miss: Cache returns null; application queries the database (PostgreSQL), writes the result into cache with a TTL (redis.set EX), and returns the response.
Benefits: Only requested data is cached (saves RAM), and if Redis crashes or reboots, the application gracefully degrades by falling back to PostgreSQL without failing.

Q3: What is "Proactive Cache Warming" (Write-Through Caching) vs Cache-Aside?
Interviewer's Goal: Tests deeper architectural variations in caching strategies.

In standard Cache-Aside, the very first user who accesses a new link always experiences a slow Cache Miss because the cache is cold.

In our POST /api/urls endpoint, we implemented Cache Warming: the moment a link is inserted into PostgreSQL, we immediately write it to Redis (await redis.set('url:' + code, url, 'EX', 86400)). This ensures that even the very first visitor to that link gets a sub-2ms Cache Hit.

Q4: What is TTL (Time-To-Live), and what happens when it expires?
Interviewer's Goal: Tests cache lifecycle management and memory constraints.

TTL (Time-To-Live) is an expiration timer attached to a cache key (in our code, EX 86400 = 24 hours).

When the TTL counter reaches zero, Redis marks the key as expired and automatically cleans it up from RAM (using active and passive expiration algorithms). This prevents abandoned or unpopular URLs from consuming expensive RAM indefinitely. If the link is accessed again later, Cache-Aside simply repopulates it from PostgreSQL.

Q5: What happens when Redis memory gets completely full? What are Eviction Policies (LRU vs LFU)?
Interviewer's Goal: Evaluates production-readiness under memory pressure.

When Redis reaches its maximum memory limit (maxmemory), it applies a configured Eviction Policy:

  • allkeys-lru (Least Recently Used): Evicts the keys that haven't been accessed for the longest time. (Best for URL shorteners).
  • allkeys-lfu (Least Frequently Used): Evicts the keys accessed least often overall.
  • volatile-lru / volatile-ttl: Only evicts keys that have an explicit TTL set.
  • noeviction: Returns an out-of-memory error on write operations while still allowing reads.

Q6: What is a "Cache Hit Ratio", and why is it a vital monitoring metric?
Interviewer's Goal: Tests telemetry, observability, and production health monitoring.

The Cache Hit Ratio measures the percentage of requests successfully served from cache versus total requests:
Hit Ratio = Cache Hits / (Cache Hits + Cache Misses)

In a healthy URL shortener, the Hit Ratio should be 85%–98%. If the Hit Ratio drops (e.g. to 40%), it indicates that TTLs may be too short, Redis memory is too small (causing aggressive evictions), or traffic patterns have shifted, causing excessive load on the PostgreSQL database.

Q7: What is the "Cache Stampede" (Thundering Herd) problem, and how do you prevent it?
Interviewer's Goal: Senior-level concurrency question on high-traffic cache misses.

A Cache Stampede occurs when an extremely popular link's cached key expires during peak traffic. If 10,000 users click the link at the same second, all 10,000 requests experience a simultaneous Cache Miss and simultaneously bombard PostgreSQL with identical queries, overwhelming database CPU and connection pools.

Solutions:

  1. Mutual Exclusion (Mutex / Distributed Locks): Only the first request acquires a lock to query the DB and update Redis; others wait or retry.
  2. Probabilistic Early Expiration (XFetch): Pre-emptively refresh the cache in the background before the TTL officially expires.

Q8: What is "Cache Penetration", and how did our code mitigate it?
Interviewer's Goal: Tests resilience against malicious traffic and non-existent keys.

Cache Penetration happens when malicious actors or bots repeatedly request non-existent short codes (e.g., /nonexistent123). Because the key never exists in Redis, every single request bypasses the cache and forces a disk query against PostgreSQL.

Mitigation:

  • Cache Null Objects: Store redis.set('url:nonexistent', '', 'EX', 60) with a short 60s TTL so repeated queries hit cache.
  • Bloom Filters: Use a Bloom filter in front of Redis to quickly verify whether a short code exists before querying storage.

Q9: Why is Redis single-threaded, and how can it handle 100,000+ operations/sec?
Interviewer's Goal: Tests understanding of event-driven architectures and non-blocking I/O.

Redis executes all command logic on a single main thread using an event-driven I/O multiplexing model (similar to Node.js's event loop).

It is extremely fast because:

  1. Zero Thread Context Switching: Multi-threaded architectures waste substantial CPU cycles switching thread contexts and managing locks. Redis has zero locking overhead.
  2. In-Memory Operations: Memory lookups take nanoseconds, meaning CPU processing is never the bottleneck; network bandwidth is.
  3. I/O Multiplexing (epoll/kqueue): A single thread monitors thousands of network client sockets simultaneously without blocking.

Q10: Why did we attach custom headers X-Cache: HIT and X-Cache: MISS?
Interviewer's Goal: Tests observability, debugging, and CDN proxy conventions.

X-Cache is an industry-standard HTTP response header used by reverse proxies and CDNs (such as Cloudflare, NGINX, Fastly, and AWS CloudFront).

By returning X-Cache: HIT or X-Cache: MISS along with X-Response-Time, frontend developers, monitoring agents, and automated test suites can verify cache behavior directly via HTTP response headers without needing server log access.
