Q1: What is Base62 encoding, and why do URL shorteners use it instead of Base64 or Hexadecimal?
Interviewer's Goal: Tests understanding of URL-safe character sets and compact encoding.

Base62 uses 62 alphanumeric characters: digits 0-9 (10), lowercase a-z (26), and uppercase A-Z (26).

We use Base62 because all 62 characters are completely URL-safe. Base64 includes special symbols like + and /, which have reserved syntactic meanings in URLs and require percent-encoding (e.g. %2F), breaking links or causing formatting issues. Hexadecimal (Base16) uses only 16 characters, resulting in significantly longer, less compact strings.

Q2: Why not just use MD5, SHA-256, or random strings? What is the Hash Collision problem?
Interviewer's Goal: Tests algorithmic reasoning, hashing limitations, and database efficiency.

Random strings or truncated cryptographic hashes (like MD5 or SHA-256) inevitably suffer from Hash Collisions due to the Birthday Paradox as the dataset expands. To resolve collisions, the server must repeatedly query the database (SELECT id FROM urls WHERE short_code = ...) to verify uniqueness before inserting, causing major performance bottlenecks.

Base62 converts the database's auto-incrementing Primary Key ID. Because each database ID is guaranteed to be strictly unique, Base62 guarantees mathematically zero collisions with zero database lookup overhead.

Q3: How many unique 6-character short codes can Base62 produce? Walk me through the math.
Interviewer's Goal: Tests combinatorial arithmetic and capacity planning.

With 6 character positions and 62 possible characters per position, the total capacity is:
62⁶ = 62 × 62 × 62 × 62 × 62 × 62 = 56,800,235,584

That is over 56.8 billion unique links with just 6 characters. Even if the service generated 1,000 new links every second around the clock, it would take nearly 1.8 years of continuous generation to exhaust the 6-character space.

Q4: Why did we use BigInt in base62.js instead of standard JavaScript Number?
Interviewer's Goal: Tests deep JavaScript runtime knowledge regarding numeric precision.

Standard JavaScript numbers are IEEE 754 double-precision floating-point numbers. Their maximum safe integer (Number.MAX_SAFE_INTEGER) is 2⁵³ - 1 (≈ 9.007 × 10¹⁵).

Our PostgreSQL database uses BIGSERIAL (a 64-bit signed integer supporting up to 9 × 10¹⁸). If a database ID exceeds 2⁵³, standard JavaScript numbers will silently round and corrupt the value. Using BigInt guarantees exact integer arithmetic on arbitrary-precision 64-bit numbers without loss of precision.

Q5: What is the difference between an HTTP 301 and an HTTP 302 redirect? Why do URL shorteners use 302?
Interviewer's Goal: Essential system design question regarding HTTP caching vs telemetry tracking.

An HTTP 301 (Moved Permanently) tells the client browser to cache the target URL locally in browser memory forever. Subsequent visits bypass our backend entirely—making it impossible to record click telemetry or analytics!

An HTTP 302 (Found / Temporary Redirect) instructs the browser to redirect immediately but prevents the browser from caching the response. Every click hits our server, enabling complete click telemetry capture (Country, Device, Referrer, Timestamp) on every visit.

Q6: What is a Database Connection Pool (pg.Pool), and why is it better than pg.Client?
Interviewer's Goal: Tests knowledge of TCP latency, resource contention, and scalability.

Establishing a fresh database connection requires TCP handshakes, SSL handshakes, and authentication negotiation, taking 30–50ms. Opening a new connection per HTTP request (pg.Client) would quickly exhaust PostgreSQL's max_connections limit under concurrent traffic and cause server crashes.

A Connection Pool maintains a set of reusable, pre-warmed connections. Requests borrow an available connection in under 0.1ms, execute their query, and return it to the pool immediately.

Q7: What does "Lazy Initialization" mean regarding pg.Pool?
Interviewer's Goal: Tests understanding of library lifecycle and memory management.

When new Pool() is declared in Node.js, it does not immediately connect all 20 sockets to PostgreSQL. It waits "lazily" until the application actually executes its first query (e.g. pool.query). Only when traffic demands a connection does it establish the socket. This ensures idle applications do not hold unnecessary database connections open.

Q8: In POST /api/urls, why did we first insert a row and then update it with the Base62 code?
Interviewer's Goal: Tests understanding of database sequences and auto-increment mechanics.

In PostgreSQL, an auto-incrementing ID is generated by a database sequence upon row insertion. To know the ID so we can encode it into Base62, we first insert the record to obtain the generated id, calculate the Base62 code in application memory, and update the row.

In extreme high-throughput systems, an alternative pattern is calling SELECT nextval('urls_id_seq') to reserve the sequence number beforehand, allowing a single combined INSERT statement.

Q9: How do Custom Vanity Slugs (e.g., /my-resume) work alongside auto-generated Base62 codes?
Interviewer's Goal: Tests schema constraints, conflict resolution, and indexed routing.

Our urls table includes both short_code and custom_alias columns with UNIQUE constraints. When a user requests a custom slug, the API verifies that the alias is not already in use as either a custom slug or an existing Base62 code.

In GET /:code, our query checks WHERE short_code = $1 OR custom_alias = $1, leveraging our B-Tree index to resolve both types uniformly in under 2ms.

Q10: Why did we update clicks_count asynchronously without await in GET /:code?
Interviewer's Goal: Tests understanding of latency optimization and event-loop non-blocking I/O.

In GET /:code, the top priority is redirect latency (< 25ms). The user should never wait for an internal analytics counter update before being redirected.

By executing pool.query('UPDATE urls SET clicks_count...') without await, Express immediately sends the HTTP 302 redirect response while PostgreSQL processes the counter increment in the background without blocking the HTTP response.
