Day 7 System Design Foundations Summary:

  • Read-to-Write Ratio: 100:1 read-dominant system (~40 write QPS vs. ~4,000 read QPS).
  • 5-Year Storage: 3 TB for 6 billion short links; 120 TB for 600 billion telemetry clicks.
  • Memory Sizing (80/20 Rule): Caching the 20% most popular links requires < 1 GB of Redis RAM.
  • Asynchronous Decoupling: Low-latency redirects (< 2ms) separated from analytics writes via BullMQ.
  • Fault-Tolerance: Fail-open rate limiting and cache-aside fallbacks preventing cascading service failures.
Q1: How do you calculate traffic, storage, and cache memory requirements for a URL shortener during an interview?
Interview Goal: Demonstrate structured back-of-the-envelope estimation and engineering sizing.
Answer:
Always establish the Write vs. Read baseline first:
  • Traffic (QPS): Assume 100M new URLs/month. Seconds in a month = $30 \times 24 \times 3,600 \approx 2.6\text{M}$.
    Write QPS = $100\text{M} / 2.6\text{M} \approx \mathbf{40\text{ writes/sec}}$.
    Because URL shorteners have a 100:1 read ratio, Read QPS = $40 \times 100 = \mathbf{4,000\text{ reads/sec}}$ (Peak: ~8,000 QPS).
  • Storage (5 Years): 100M/month $\times$ 60 months = 6 billion URLs. At 500 bytes/row, total URL storage = $6\text{B} \times 500\text{B} \approx \mathbf{3\text{ TB}}$ (easily fits on a single managed database disk).
    For 600 billion clicks at 200 bytes/row = $\mathbf{120\text{ TB}}$ (requires partitioning and archiving).
  • Cache Memory (80/20 Pareto Rule): 80% of redirect traffic hits 20% of trending links. Daily clicks = $4,000 \times 86,400 \approx 345\text{M}$. Caching 20% of active daily links (~600K keys at 250 bytes) requires only $\approx \mathbf{150\text{ MB}}$ of RAM. Even caching 20 million hot links requires only 5 GB of Redis RAM.
Q2: Why did we choose Base62 encoding over MD5/SHA-256 hashes or UUIDs for generating short codes?
Interview Goal: Compare slug generation strategies, collision mitigation, and URL length optimization.
Answer:
There are three common approaches, but Base62 derived from an auto-increment sequence is mathematically superior:
  • UUIDv4: 36 characters long (e.g., 123e4567-e89b-12d3-a456-426614174000). Defeats the purpose of a URL shortener.
  • MD5 / SHA-256 Hash Truncation: Hashing the original URL and taking the first 6 characters leads to hash collisions (birthday paradox). Handling collisions requires querying the database, detecting conflicts, appending a salt, and rehashing in a loop, introducing unpredictable write latency.
  • Bijective Base62 Encoding (PulseLink Choice): Base62 maps a 64-bit integer ID directly to 6 characters (using 0-9, a-z, A-Z).
    Advantages: $62^6 = 56,800,235,584$ (56.8 billion) unique codes. It is a 1-to-1 bijection, meaning zero collisions by definition, deterministic execution, and zero retry loops.
Q3: How do you prevent users from guessing sequential URLs in a Base62 system?
Interview Goal: Address security vulnerabilities in sequence-based ID generators (enumeration attacks).
Answer:
If database IDs increment sequentially (1, 2, 3...), short codes increment sequentially (000001 → 000002 → 000003). Competitors or attackers could scrape the entire database using an enumeration script.

Production Solutions:
  1. Feistel Cipher / Bit Permutation: Pass the auto-increment integer ID through a lightweight pseudo-random permutation function (like a 3-round Feistel cipher or Skip32) before Base62 encoding. The transformation is 1-to-1 and reversible, but consecutive numbers appear completely random (e.g., ID 1 → xK9w2Z, ID 2 → aB4pQ1).
  2. Distributed Snowflake ID: Use a 64-bit Twitter Snowflake ID (Timestamp + Machine ID + Sequence bits). The higher-order bits are non-linear, masking predictable sequences.
  3. Token Range Pre-allocation: Pre-generate blocks of random unique IDs into Redis sets or an ID generation service (like ZooKeeper) and pop tokens atomically.
Q4: What is the Cache-Aside pattern, and what happens during a Cache Stampede or Cache Avalanche?
Interview Goal: Explain cache architectures, failure modes, and mitigation strategies.
Answer:
In Cache-Aside (Lazy Loading), the application checks Redis first. On a Cache Hit, it returns data immediately (< 2ms). On a Cache Miss, it reads from PostgreSQL, returns the result, and writes it to Redis with an expiration TTL (24 hours).

Critical Failure Modes & Mitigations:
  • Cache Avalanche: Many cached keys expire at the exact same second, causing thousands of requests to hit PostgreSQL simultaneously.
    Mitigation: Add randomized jitter to TTLs (e.g., $86400 \pm \text{random}(0, 3600)$ seconds).
  • Cache Stampede (Thundering Herd): A viral link's cache key expires, and 5,000 concurrent requests all miss Redis simultaneously, overloading the database with 5,000 identical queries.
    Mitigation: Use a Mutex / Distributed Lock in Redis (only one thread queries Postgres and repopulates cache; others wait 50ms) or Probabilistic Early Expiration (XFetch).
  • Cache Penetration: Attackers request non-existent short codes (e.g., /fake999) that are never in Redis, forcing constant database queries.
    Mitigation: Cache null values for 60 seconds or use a Bloom Filter in front of Redis.
Q5: Why did we use BullMQ and an asynchronous message queue for telemetry instead of writing directly to PostgreSQL?
Interview Goal: Explain architectural decoupling, write throughput buffering, and latency optimization.
Answer:
If click telemetry is written synchronously inside GET /:code:
  1. Latency Penalty: The user's redirect must wait for GeoIP lookup, User-Agent parsing, SHA-256 IP hashing, and a PostgreSQL disk insert, increasing redirect latency from 2ms to 40ms+.
  2. Database Connection Pool Exhaustion: During a traffic spike (e.g., a viral Super Bowl tweet receiving 10,000 clicks/sec), PostgreSQL's connection pool (typically 20-50 connections) would saturate immediately, crashing the redirect gateway.
BullMQ Solution:
Redis memory pushes take < 0.5ms. The gateway pushes the job and returns an instant HTTP 302 redirect (Fire-and-Forget). The BullMQ worker drains the queue at a controlled, sustainable rate (e.g., concurrency: 5), acting as a shock absorber that protects PostgreSQL from spiky write surges.
Q6: How would you scale the PostgreSQL database when the clicks table reaches 120 Terabytes?
Interview Goal: Demonstrate database scaling strategies, indexing tradeoffs, and data lifecycle management.
Answer:
At 120 TB, traditional B-tree indexes cannot fit in RAM, causing severe disk thrashing. We apply a 3-tier scaling strategy:
  1. PostgreSQL Declarative Table Partitioning (Range by Month): 
    CREATE TABLE clicks (...) PARTITION BY RANGE (clicked_at);
CREATE TABLE clicks_2026_10 PARTITION OF clicks
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
    Queries for "last 24 hours" or "this month" only scan the latest partition (Partition Pruning), keeping active index trees tiny and in RAM.
  2. Read-Heavy Analytics Read Replicas: Route GET /api/urls/:code/analytics queries to read replicas using asynchronous streaming replication, keeping the primary database dedicated strictly to writes.
  3. Cold Storage Archival (OLAP Offloading): Clicks older than 90 days are archived via a cron job to Amazon S3 in Parquet format. For enterprise querying, sync older data into a columnar OLAP database like ClickHouse or BigQuery, where aggregation queries over billions of rows run in milliseconds.
Q7: Why does PulseLink hash IP addresses with SHA-256, and what privacy regulations does this satisfy?
Interview Goal: Address data privacy, GDPR compliance, and security best practices.
Answer:
Under the General Data Protection Regulation (GDPR) and California Consumer Privacy Act (CCPA), an IPv4 or IPv6 address is legally classified as Personally Identifiable Information (PII) because it can identify an individual household or device.

Engineering Strategy:
  • Storing raw IP addresses in database tables requires user consent, data deletion workflows (Right to be Forgotten), and heavy compliance overhead.
  • We perform a one-way SHA-256 cryptographic hash before saving: 
    const ipHash = crypto.createHash('sha256').update(ip).digest('hex');
  • Why this satisfies both analytics and privacy: The raw IP is never written to disk or logs. However, the hash is deterministic, allowing our SQL query to compute accurate COUNT(DISTINCT ip_hash) (Unique Visitors) without storing sensitive user identities.
Q8: Why did we choose a Fixed Window Counter for rate limiting, and what are its tradeoffs vs. Sliding Window and Token Bucket?
Interview Goal: Compare distributed rate limiting algorithms and their implementation costs.
Answer:
We used Redis INCR + EXPIRE on key ratelimit:{ip}:{windowBucket}:
  • Fixed Window Counter (PulseLink):
    Pros: Extremely fast (atomic single-command execution in < 1ms), minimal memory footprint (1 integer per IP).
    Cons: Boundary Bursting: A user can send 5 requests at 00:59 and 5 requests at 01:01 (10 requests within a 2-second span), momentarily exceeding the rate limit.
  • Sliding Window Log:
    Pros: 100% mathematically accurate; eliminates boundary bursts.
    Cons: Stores a Redis Sorted Set (ZSET) of timestamps for every single request. Consumes massive memory under high traffic.
  • Token Bucket / Leaky Bucket:
    Pros: Smooths out bursts while allowing configured peak spikes; widely used in AWS API Gateway and Stripe.
    Cons: Requires tracking fractional token replenishment timestamps, requiring custom Lua scripts in Redis.
Conclusion: For protecting URL creation endpoints, Fixed Window provides the best tradeoff between extreme throughput, zero memory bloat, and sufficient abuse protection.
Q9: What happens if Redis crashes completely? How does PulseLink handle this failure?
Interview Goal: Demonstrate high-availability awareness, fallback mechanisms, and resilience engineering.
Answer:
PulseLink employs a Graceful Degradation & Fail-Open architecture:
  1. Redirect Gateway: If Redis is unreachable, the Cache-Aside pattern catches the Redis timeout error and falls back directly to PostgreSQL. Redirects slow down from 2ms to ~40ms, but users are never dropped or returned HTTP 500 errors.
  2. Rate Limiter (Fail-Open): The rate limiter catches Redis connection errors, logs an alert, and calls next(). In production, it is safer to temporarily allow excess traffic than to block 100% of legitimate users during a cache outage.
  3. BullMQ Telemetry Queue: BullMQ queue additions are wrapped in .catch() error handlers. A Redis downtime pauses telemetry ingestion, but the core redirect path continues operating uninterrupted.
  4. High-Availability Production Fix: In production, deploy Redis Sentinel (automatic failover) or Redis Cluster with multi-AZ read replicas so a single instance crash promotes a replica in < 3 seconds.
Q10: Walk an interviewer through the complete production deployment topology of PulseLink at scale.
Interview Goal: Illustrate enterprise cloud infrastructure, load balancing, and multi-tier architecture.
Answer:
At enterprise scale, PulseLink deploys across four tiers:
  • 1. Edge Tier (Cloudflare / AWS CloudFront): Edge CDN caches 302 redirects for top viral URLs at points-of-presence globally, resolving clicks in < 10ms without ever reaching origin servers. WAF blocks DDoS attacks.
  • 2. Application Tier (AWS ECS / Kubernetes): Stateless Node.js Express containers auto-scale horizontally based on CPU and request latency metrics behind an Application Load Balancer (ALB).
  • 3. In-Memory Tier (AWS ElastiCache Redis Cluster): Multi-node Redis cluster with automatic sharding and replication. Handles primary Cache-Aside lookups and rate limiting.
  • 4. Persistence Tier:
    • AWS Aurora PostgreSQL (Primary + 3 Read Replicas): Write traffic (new URLs and BullMQ worker click inserts) hits Primary. Analytical dashboard queries hit Read Replicas.
    • Amazon S3 + ClickHouse / Athena: Cold clickstream data archived monthly for long-term analytical queries.
