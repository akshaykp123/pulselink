Q1: What is a Message Queue, and why use BullMQ instead of processing telemetry inside the HTTP request?
Interviewer's Goal: Tests understanding of synchronous vs asynchronous architectures and request latency.

A Message Queue is an asynchronous communication buffer that decouples the producer of a task from the consumer that executes it.

Processing telemetry synchronously inside the redirect route (SHA-256 hashing, GeoIP lookup, User-Agent parsing, database writes) increases latency to 80–150ms. Under high concurrent traffic (e.g. 5,000 clicks/sec), database connection pools exhaust and crashes occur.

With BullMQ, the redirect route enqueues a lightweight job payload into Redis in < 0.5ms and returns an instant HTTP 302 redirect (1.49ms). The background worker drains the queue smoothly at its own pace without impacting user latency.

Q2: Explain the Producer-Consumer pattern in our project.
Interviewer's Goal: Tests understanding of fundamental asynchronous software design patterns.

Our project implements the Producer-Consumer pattern across three components:

  • The Producer: The Express route GET /:code. When a link is clicked, it creates a job payload containing { urlId, ip, userAgent, referer } and calls telemetryQueue.add().
  • The Queue Broker: Redis, which stores the job payload safely in memory.
  • The Consumer: Our telemetryWorker in src/workers/telemetryWorker.js. It listens to Redis, consumes jobs, parses the telemetry metadata, and executes the SQL INSERT into PostgreSQL.

Q3: Why didn't we use await telemetryQueue.add(...) in server.js? What is "Fire-and-Forget"?
Interviewer's Goal: Tests knowledge of non-blocking I/O and latency optimization.

We intentionally omitted await to implement the Fire-and-Forget pattern.

In a redirect service, the absolute highest priority is redirecting the user immediately (< 2ms). Enqueueing is a background task. By not awaiting the promise, Express dispatches the HTTP 302 response immediately without waiting for the network roundtrip to Redis.

We attach a .catch() handler so that if Redis encounters a transient failure, the error is logged in the background without breaking or blocking the visitor's browsing experience.

Q4: What happens if PostgreSQL crashes while the worker processes a click? What is Exponential Backoff?
Interviewer's Goal: Tests fault-tolerance, resilience, and retry mechanisms.

Because we configured BullMQ with attempts: 3 and backoff: { type: 'exponential', delay: 1000 }, no click events are lost:

  1. If PostgreSQL throws a connection error on attempt 1, BullMQ marks the job for retry.
  2. It waits 1 second (1000 × 2⁰) before retry 1.
  3. If that fails, it waits 2 seconds (1000 × 2¹) before retry 2.
  4. If that fails, it waits 4 seconds (1000 × 2²) before attempt 3.
This prevents hammering a struggling database and gives it time to recover from temporary spikes.

Q5: Why did we upgrade the Redis cache to store a JSON object { id, originalUrl } instead of just a string?
Interviewer's Goal: Tests foresight in cache design and eliminating secondary database queries.

On a Cache Hit, the server resolves the redirect directly from Redis without touching PostgreSQL.

However, our BullMQ telemetry worker requires the url_id to link the click record in PostgreSQL via a Foreign Key. If Redis only stored the destination URL string, a Cache Hit would force us to query PostgreSQL just to look up the URL's integer ID, defeating the purpose of the cache!

By caching { id, originalUrl } as a compact JSON object, we resolve BOTH the redirect URL and the ID directly from RAM in 1.49ms.

Q6: What is the difference between x-forwarded-for and req.socket.remoteAddress?
Interviewer's Goal: Tests real-world networking, load balancers, and reverse proxy mechanics.

req.socket.remoteAddress is the IP address of the direct physical TCP socket connected to our server.

In production, applications sit behind reverse proxies, load balancers, or CDNs (Cloudflare, AWS ALB, NGINX). If we only read socket.remoteAddress, every visitor's IP would be Cloudflare's internal proxy IP.

The proxy inserts the original visitor's real public IP into the X-Forwarded-For HTTP header. Our code checks x-forwarded-for first for production proxies, falling back to socket.remoteAddress for local development.

Q7: Why do we hash the visitor's IP address with SHA-256 before storing it?
Interviewer's Goal: Tests cybersecurity, data privacy, and GDPR/CCPA compliance awareness.

Under privacy laws like GDPR and CCPA, IP addresses are classified as Personally Identifiable Information (PII). Storing raw IP addresses exposes companies to legal penalties and security leaks in the event of a database breach.

By hashing the IP using SHA-256, the result is mathematically irreversible (one-way). Because identical IPs produce identical hashes, we can still run COUNT(DISTINCT ip_hash) in SQL to calculate Unique Visitors accurately without retaining any private user data.

Q8: How does geoip-lite resolve countries and cities in < 0.1ms without external APIs?
Interviewer's Goal: Tests understanding of embedded binary lookup datasets vs HTTP microservices.

geoip-lite does not make slow HTTP requests to third-party web services. Instead, it embeds a local, pre-indexed binary database (MaxMind GeoLite) directly in the local file system.

It converts the visitor's IPv4/IPv6 address into an integer and executes an in-memory binary search over indexed address ranges. This completes in under 0.1 milliseconds, eliminating network roundtrips and external API rate limits entirely.

Q9: What is the concurrency setting in BullMQ Worker, and why is it important?
Interviewer's Goal: Tests Node.js event-loop asynchronous throughput.

By default, a BullMQ Worker processes jobs sequentially one at a time (concurrency: 1). If writing to PostgreSQL takes 20ms, the worker would cap out at 50 jobs per second.

By setting concurrency: 5, our single worker pulls up to 5 jobs simultaneously from Redis, leveraging Node.js's asynchronous non-blocking I/O to perform multiple database inserts concurrently, multiplying background throughput by 5x without creating extra worker processes.

Q10: Why did we set removeOnComplete: true in telemetryQueue.js?
Interviewer's Goal: Tests Redis memory hygiene and prevention of memory leaks.

By default, BullMQ retains completed job data in Redis for debugging and inspection.

In a high-throughput URL shortener processing millions of clicks, storing millions of completed job objects in Redis would rapidly exhaust expensive RAM. Setting removeOnComplete: true instructs BullMQ to automatically purge the job from Redis the moment the worker finishes, ensuring Redis RAM usage remains strictly bounded.
